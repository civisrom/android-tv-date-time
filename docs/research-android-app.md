# Исследование: Android-приложение вместо десктопной версии

Проведено 2026-09-02. Вопрос пользователя: насколько просто и целесообразно
сделать Android-версию Android TV Time Fixer, ориентир — устаревшее
[Remote ADB Shell](https://play.google.com/store/apps/details?id=com.cgutman.androidremotedebugger),
меню и функционал — как у текущей Windows-версии.

## Краткий вывод

**Технически проще, чем десктопная версия.** Ядро (`settings put global
ntp_server` через ADB) воспроизводится 1-в-1 современными Kotlin-библиотеками.
С Android отпадают три самых грязных куска десктопного кода: управление внешним
бинарником `adb`, `psutil` и ~400 строк платформенных хаков определения
маршрутов.

**Целесообразно — да,** но ценность не в «порте», а в снятии барьера «нужен ПК».
Аудитория — люди с Android TV и телефоном в той же Wi-Fi-сети.

**Главный риск — не код, а публикация в Google Play.**

## Почему референс устарел

`com.cgutman.androidremotedebugger` построен на
[AdbLib](https://github.com/cgutman/AdbLib), которая реализует только старую
схему аутентификации (RSA-ключ + запрос на экране), то есть подключение к
`IP:5555`. С Android 11 появилась беспроводная отладка с TLS-1.3, спариванием по
коду и mDNS-анонсом — AdbLib этого не умеет. Отсюда жалобы «prompt не
появляется». **Вывод: AdbLib не брать.**

## Выбор ADB-библиотеки

| Библиотека | Координаты | Лицензия | Работает *на* Android | TLS-пэйринг | Оценка |
|---|---|---|---|---|---|
| **Kadb** ([flyfishxu/Kadb](https://github.com/flyfishxu/Kadb)) | `com.flyfishxu:kadb:2.1.3` + `kadb-mdns` | Apache-2.0 | да, `minSdk 23` | **да** | **рекомендуется** |
| dadb ([mobile-dev-inc](https://github.com/mobile-dev-inc/dadb)) | `dev.mobile:dadb` | Apache-2.0 | заявлена host→device (JVM) | не документирован | запасной |
| AdbLib (cgutman) | — | — | да | нет | не брать |

Kadb закрывает весь нужный набор: shell + PTY (под «режим терминала»),
push/pull, install, port-forward, mDNS-обнаружение, спаривание. Оговорка: для
пэйринга на JVM нужен Conscrypt, на Android 6–8 — своя конфигурация.

**Внешний бинарник `adb` в приложении не нужен вообще.**

## Перенос функционала: пункт за пунктом

| Пункт меню десктопа | Как на Android | Сложность |
|---|---|---|
| 1–2. NTP по коду страны / вручную | `kadb.shell("settings put global ntp_server …")` | тривиально |
| 3–4. Списки стран (65) и альт. серверов (110+) | те же данные + `LazyColumn` с поиском | тривиально |
| 5. Инфо об устройстве | `getprop`, `dumpsys` — те же команды | тривиально |
| 6. Пинг NTP (RTT, % успеха) | `DatagramSocket` :123, ~80 строк своего SNTP, или `commons-net`. `android.net.SntpClient` — `@hide`, не использовать | легко |
| 7. Избранное, буфер, экспорт/импорт | `ClipboardManager`; SAF (`ACTION_CREATE_DOCUMENT`/`OPEN_DOCUMENT`) — без разрешений | легко |
| 8. Сканирование сети | `ConnectivityManager.getLinkProperties()` → подсеть, корутины. Взамен ~400 строк `_get_*_default_route_ips` | легко, стало проще |
| 9. Авто-режим | та же логика, регион из `TimeZone.getDefault()` | средне |
| 10. Режим терминала | Kadb PTY-shell + `TextField` | средне (UI) |
| Локализация (221 ключ) | `strings.xml` ru/en | механически |

Плюс новое: спаривание по коду для Android 11+ и mDNS-обнаружение — то, чего в
десктопной версии на момент исследования не было.

## Подводные камни (по убыванию важности)

1. **Разрешение на локальную сеть.** В Android 16 (targetSdk 36) — opt-in
   (тест через `NEARBY_WIFI_DEVICES`), в **Android 17 (targetSdk 37) —
   обязательное runtime-разрешение `android.permission.ACCESS_LOCAL_NETWORK`**
   из группы `NEARBY_DEVICES`. Без него все сокеты в 192.168.x.x падают.
   Приложение на 100% про LAN → закладывать сразу.
2. **Google Play target API.** С 31 августа 2026 новые приложения и обновления
   должны целиться в API 36 (продление до 1 ноября 2026 по заявке). Дедлайн уже
   прошёл — сразу `targetSdk 36`. Для Android TV-приложений требование мягче:
   API 34+.
3. **«Отладка по сети» на самом TV.** Многие прошивки сбрасывают её после
   перезагрузки — а перезагрузка и есть сценарий проблемы.
4. **Одноразовость.** NTP-сервер выставляется один раз. Пользователь поставит
   приложение, применит и удалит. Аргумент против вылизанного паритета со всеми
   10 пунктами и за компактный MVP.
5. **Буфер обмена.** Android 10+ запрещает чтение в фоне, 12+ показывает тост.
   «Вставить сервер из буфера» лучше заменить полем ввода + кнопкой.
6. **Cleartext-политика — не проблема:** ADB это сырой TCP-сокет,
   `usesCleartextTraffic`/Network Security Config к нему не применяются.

## Что переиспользуется из Python-кода

Честно: **кода — 0%**, это переписывание, а не порт. Переносится дизайн и данные:
таблицы NTP (65 стран + ~110 серверов), регулярки валидации, логика
`_test_ntp_server`, определение региона по таймзоне, стратегия сканирования,
221 строка локализации — ≈30–35% ценности. Выбрасывается: 236 `print` +
32 `input` + 237 `Fore.*`, `ADBProcessManager`, `get_adb_path` + hooks, `psutil`,
платформенные маршруты.

**Альтернатива с переиспользованием Python:**
[Chaquopy](https://chaquo.com/chaquopy/license/) (с 12.0.1 — MIT, бесплатно,
есть бинарные пакеты вроде `cryptography`) позволил бы затащить `adb_shell` и
ядро как есть. Но: +20–40 МБ к APK, задержка старта, ограничение 16 КБ page
size, и всё равно нужен рефакторинг headless-ядра. **Не рекомендуется** —
Kotlin + Kadb чище и меньше.

## Отдельная идея, возможно лучшая

Сборка **прямо для Android TV**, подключающаяся к `127.0.0.1:5555` — к adbd
своего же устройства. Пользователь включает «Отладку по сети», ставит APK,
приложение коннектится к самому себе, на экране появляется штатный запрос
авторизации, приложение прописывает `ntp_server`. **Ни ПК, ни телефона, ни
знания IP.** Loopback под ограничения локальной сети не подпадает, требования
Play к Android TV мягче (API 34+).

Проверить на реальном железе: не все прошивки принимают adb-подключение с самих
себя. Если работает — радикально лучший UX и буквально пара сотен строк.

Прямое «приложение на TV меняет настройку само» без ADB невозможно:
`settings put global` требует `WRITE_SECURE_SETTINGS` (`signature|privileged`),
которое обычному APK выдаётся только через adb/root/Shizuku.

## Оценка трудозатрат

| Объём | Строк Kotlin | Срок (1 разработчик, Compose знаком) |
|---|---|---|
| **MVP**: подключение по IP + пэйринг, NTP по стране/вручную, текущие настройки, инфо об устройстве, ru/en | 1500–2000 | 5–8 дней |
| **+** сканирование сети, пинг NTP, избранное, экспорт/импорт | +1500 | +1.5–2 недели |
| **Полный паритет** (авто-режим, групповое обновление, терминал) | 4500–6000 | 3–5 недель суммарно |
| TV-сборка через loopback | +200–300 | +2–3 дня |

## Рекомендация

1. Начать с **MVP на Kotlin + Compose + Kadb**, `targetSdk 36`, с заложенным
   `ACCESS_LOCAL_NETWORK`.
2. Параллельно за пару дней проверить **loopback-гипотезу на TV** — если
   сработает, это станет главным сценарием.
3. **Распространение — GitHub Releases (APK) + F-Droid** как основной канал;
   Play — потом и опционально. Аудитория уже качает утилиту с GitHub, а Play
   добавляет постоянное обслуживание target API ради приложения, которое
   запускают один раз.
4. Не тащить сразу все 10 пунктов меню: на телефоне пункты 3, 4, 7 схлопываются
   в один экран со списком и поиском.
